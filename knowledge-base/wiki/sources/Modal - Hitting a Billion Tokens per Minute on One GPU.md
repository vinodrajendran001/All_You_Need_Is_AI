# Modal - Hitting a Billion Tokens per Minute on One GPU

## Summary

Modal, with Carnegie Mellon's Full Stack Data Lab, introduces Quail: an inference layer that sees the
SQL query plan before execution and co-optimizes join ordering, KV-cache reuse, prefetching, and GPU
kernels against it. The workload is AI-SQL, which builds prompts from database rows and returns
relational results; it is prefill-only Boolean and classification inference with no decode. Because
the future request order is known, Quail can evict exactly and prefetch deliberately rather than
guess. Modal reports over a billion tokens processed per minute per H100 on one multi-join query and
a 1.84x geometric-mean advantage over vLLM across its released benchmark.

## Key claims

- AI-SQL is not NL2SQL: it constructs prompts from rows and returns a relation. Requests are
  generated by the planner, not by users, so the engine may see the whole future workload at once.
- Reported performance: **over a billion tokens processed per minute per H100 GPU**, **>10x faster
  than the vLLM baseline** on one multi-join query, at **under 6 cents per billion tokens** on Modal.
- Across the released AI-SQL benchmark the advantage is **1.84x faster than vLLM, geometrically
  averaged** - and Modal states Quail *falls behind* vLLM on an agent-trace benchmark. Two benchmark
  queries were deliberately designed to expose future weaknesses.
- Planner mechanisms: predicate pushdown, selectivity-based filter ordering, dynamic-programming join
  ordering, KV-aware plan search, and Pareto pruning over token count, attention pairs, and cached
  tokens, costed by a roofline speed-of-light model.
- Because Boolean filters need only one output token, Quail implements **no separate prefill/decode
  phases, no prefill-decode disaggregation, no sampling, no CUDA Graph capture, and no speculative
  decoding**.
- The output vocabulary is reduced to **8 options** for truthy/falsy filtering, shrinking the final
  unembedding from vocabulary-size x latent-size to **8 x latent-size**. Suffix KV is never written to
  cache because there is zero decode and joins are never more than two-way.
- Kernels: fused add-RMSNorm with FP8 quantization, fused per-head query/key RMSNorm with rotary
  embeddings, and recursive combination-of-partials attention for shared join anchors, on DeepGEMM
  and FlashAttention 3. Stack is `sqlglot`, a custom planner, a vLLM-derived forward pass, PyArrow
  columnar storage, and Triton kernels.
- Because latency matters less here, a multi-tier KV cache becomes practical; cross-query KV reuse
  and radix indexing for prefix sharing remain future work.

## Why it matters

This inverts the vault's usual serving assumption. Most of the serving literature optimizes under
uncertainty about what arrives next; Quail's thesis is that a large class of valuable LLM work has a
known plan, and that knowing it converts cache policy from heuristic to scheduling. It is the
clearest case in the vault that the right serving architecture is a function of who generates the
requests, not only of the model.

## Tensions and caveats

The billion-tokens-per-minute figure belongs to one multi-join query on one model and one GPU, not to
general serving; the honest cross-workload number is the 1.84x geometric mean, and Modal publishes
its own loss on agent traces. The workload is unusually favorable: known structure, shared prefixes,
no decode, structured outputs, low latency sensitivity. Modal calls its own cost model crude and
based on peak hardware rates, which can overestimate attainable performance. Full SQL execution
support was not yet implemented. All figures are vendor-reported and the post links to Modal's
commercial service.
