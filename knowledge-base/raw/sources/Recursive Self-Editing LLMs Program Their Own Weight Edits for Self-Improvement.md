###### Abstract

Recursive self-improvement asks a system to improve the very system that improves it. Today’s language models improve themselves through data, training recipes or scaffolds; whenever their weights change, gradient descent writes the update, not the model. We let the model write its own weights. In SelfWrite, each generation the current model studies its own reasoning on fresh training problems, inspects its own weights and activations in a persistent Python session, and writes a program that constructs a low-rank weight edit for itself from white-box primitives (singular directions, activation contrasts between its right and wrong answers, rank-one projections, tensor computations), with no training or gradient tool. Every candidate is graded once on a hidden gate set against the current model; the best strictly improving edit is merged into the weights, and the edited model writes the next edit. On Qwen3.8-27B and math problems from DAPO-Math, five generations of SelfWrite raise gate accuracy from 73.95% to 76.45% and accuracy on a held-out test split that the loop never sees from 76.30% to 77.75% (avg@4) and from 82.60% to 84.80% (pass@4), without a single gradient step. A language model can author useful changes to its own weights without gradients, and the edited model keeps writing useful edits.

## 1 Introduction

A recursively self-improving system improves the very system that does the improving [^7]. Large language models now improve themselves along three routes: they generate and judge their own training *data* [^12], choose *training recipes* for themselves or other models \[seal, metarsi, ftdojo, posttrainbench\], or rewrite the *scaffolds and harnesses* around a model \[stop, godelagent, dgm, aide2, hase, selfhpo\]. In SEAL \[seal\], for example, the model writes synthetic data and hyper-parameters, and LoRA fine-tuning [^9] turns them into a weight change: the model decides what to train on, and SGD decides how every parameter moves.

We take the other route: the model writes its own weights. A model that has just answered a batch of math problems reads its own outputs, contrasts the activations of one of its layers on the problems it failed and the ones it solved, and removes the contrast direction from the layer’s output matrix with a rank-one edit. If the edited model solves more held-out problems, the edit is merged, and the edited model, now reading its own changed weights, writes the next edit. No tool computes a gradient and no training step is taken (Figure 1).

Bottom: in SelfWrite the model reads its own wrong and right answers, contrasts its activations on them, and writes a program that projects the contrast direction out of one of its layers (code simplified). The rank-one edit is merged only if it improves the model on a hidden gate set, and the edited model $M_{g+1}$ writes the next edit. No gradient tool is used and no training step is taken.

This route addresses two gaps in prior work. First, *the gradient writes the weights.* In data- and recipe-level self-improvement the model chooses the inputs of an optimiser \[seal, selfspecialization, mass, metarsi\]; methods that emit weights directly rely on generators trained for that purpose [^5] [^4]; and gradient-free weight programs are written by an external model for a different network \[wsp\] or applied to a fixed base model [^14]. Second, *the improved model rarely improves its own weights next.* SEAL discards the adapted weights after each episode, MetaRSI retrains from the base model \[seal, metarsi\], and where the updated model does take over, its weights are still changed by fine-tuning \[mass\] or it edits harnesses rather than weights \[hase, selfhpo\].

We formulate *gradient-free recursive self-editing*: in generation $g$ the current model $M_{g}$ writes a program that constructs a weight edit $\Delta_{g}$ for itself; if $\Delta_{g}$ improves $M_{g}$ on a gate set the editor never sees, it is merged, $M_{g+1}=M_{g}\oplus\Delta_{g}$, and $M_{g+1}$ writes the next edit. The editor has no gradient tool and no stronger external model, grading is deterministic, and edits are capped in rank and norm. The setting is demanding: among hundreds of weight matrices the editor must find the few directions that help reasoning, every candidate must be graded at 27B scale on long sampled reasoning traces, and the signal the editor reads must be kept apart from the decision that accepts an edit.

SelfWrite meets these requirements with four components (Figure 2). (i) Observe. Each generation, $M_{g}$ answers 500 freshly drawn training problems four times in thinking mode, and the editor can read every one of its own answers, including the full reasoning, and compute activation statistics on them. (ii) Write. The editor works in a persistent Python session for up to 30 tool rounds, with a white-box toolkit over its own weights: truncated SVD of any module, activation statistics on its own right and wrong answers, rank-one constructions and projections, singular-direction rescaling, LoRA operators, and sandboxed tensor computations on any weight; it then returns a self-contained program that builds the edit. (iii) Select on a hidden paired gate. Eight independent sessions per generation each produce one candidate; every candidate is graded once on a fixed 500-problem gate set, paired item by item with $M_{g}$, and later generations see only the statistics of earlier gate results, never a gate problem’s statement or answer. (iv) Merge and succeed. The candidate with the largest strictly positive paired gain is merged into the weights, and the merged model becomes the next editor, with a searchable history of every earlier attempt.

## 2 Related Work

#### Recursive self-improvement.

[^7] imagined machines that improve the machinery that improves them, and the Gödel machine \[godelmachine\] accepts a self-rewrite once it is proven useful. Recent LLM systems replace the proof with an empirical check and act on code: STOP \[stop\] improves a scaffold with a fixed model, Gödel Agent \[godelagent\] rewrites its runtime logic, the Darwin Gödel Machine \[dgm\] evolves coding agents around a frozen foundation model, and AIDE<sup>2</sup> \[aide2\] accepts agent rewrites that win on private held-out tasks. Closer to weights, MASS \[mass\] merges a LoRA trained on a model’s self-evaluated trajectories, SIA [^8] lets an external agent choose between harness edits and LoRA reinforcement-learning updates, and MetaRSI \[metarsi\] proposes LoRA training recipes from a bounded space. In all of them a fixed optimiser makes any weight change; in SelfWrite the model writes the change itself, and the edited model is the next editor. Because recursive self-training can drift over rounds \[recursivecollapse\], we follow AIDE<sup>2</sup> and accept an edit only on a fixed external check whose problems the editor never sees.

#### Self-improvement through data and recipes.

Models produce their own training signal by judging their responses \[selfrewarding\], proposing and solving their own tasks [^12], training experts on self-generated instructions \[selfspecialization\], or fitting temporary adapters at test time [^1]. SEAL \[seal\] writes self-edits (synthetic data and optimisation settings) that a fixed fine-tuning step applies, and searching over self-edit strategies extends this to templates and LoRA settings [^6]. Agents also run post-training pipelines \[ftdojo, posttrainbench\], write merging algorithms [^14], or alternate harness edits with fine-tuning \[hase, whale, selfhpo\]. In each case the model chooses the inputs of an optimiser and gradient descent writes the weights; in SelfWrite the program the model writes *is* the weight edit.

#### Generated weights, LoRA editing and weight-space programming.

Generative Adapter [^5] and Text-to-LoRA [^4] train a generator that maps a context to low-rank weights; Transformer<sup>2</sup> \[transformer2\] learns singular-value scaling vectors, Self-MoE \[selfmoe\] routes among self-specialised experts, and SOLAR \[solar\] trains a policy that proposes weight-adaptation strategies. LoRA [^9] and PiSSA \[pissa\] write updates as low-rank products, intruder directions characterise how LoRA changes the spectrum \[intruder\], and adapters are combined in closed form [^13] [^16], by searching merge coefficients [^11] [^3] [^15] [^2], or edited by fixed rules \[para, tada, slora\]; ROME and MEMIT write closed-form rank-one factual edits \[rome, memit\]. Weight-space programming lets an LLM write code that edits network weights [^10]. SelfWrite builds on these operators but changes who uses them and on what: the edited model itself composes them, guided by its own reasoning traces, and each accepted edit changes the model that writes the next one.

### 3.1 Setting

Let $M_{0}$ be the original model and $M_{g}$ the model after $g$ accepted generations. In generation $g$, $M_{g}$ acts as the editor and writes programs whose output is a LoRA $\Delta_{g}=\{(A_{m},B_{m})\}_{m\in\mathcal{M}_{g}}$ over a set of linear modules $\mathcal{M}_{g}$. A candidate must pass the checks

$$
\operatorname{rank}(B_{m}A_{m})\leq 64,\qquad\|B_{m}A_{m}\|_{F}\,/\,\|W_{g}^{(m)}\|_{F}\leq\tau=0.1\quad\forall m\in\mathcal{M}_{g},
$$

where $W_{g}^{(m)}$ is the current weight of module $m$, and returning no edit (keeping $M_{g}$) is always allowed. An accepted edit is merged,

$$
W_{g+1}^{(m)}=\mathrm{bf16}\big(W_{g}^{(m)}+B_{m}A_{m}\big),\qquad m\in\mathcal{M}_{g},
$$

with accumulation in FP32, and the merged model $M_{g+1}$ is the editor of generation $g+1$.

#### Data roles.

All problems come from one decontaminated training pool, split once into three disjoint parts: a *gate* set $\mathcal{G}$ of 500 problems that decides acceptance, a *test* set of 500 problems that is reported and never fed back, and the rest. Each generation draws a fresh *screen* set $S_{g}$ of 500 problems from the rest; the remaining problems form the generation’s *train* set, whose statements and gold answers programs may read. Scoring samples four answers per problem in thinking mode (temperature 0.6, top- $p$ 0.95, top- $k$ 20, up to 16,384 tokens, fixed seed), and a problem’s score $s(x)\in[0,1]$ is the fraction of correct answers under deterministic answer matching. For a candidate $c$ and the current model $M_{g}$, the paired gain on $\mathcal{G}$ is

$$
\Delta_{\mathcal{G}}(c)=\frac{1}{|\mathcal{G}|}\sum_{x\in\mathcal{G}}\big(s_{c}(x)-s_{M_{g}}(x)\big),
$$

which editors of later generations receive as feedback together with a 95% paired-bootstrap confidence interval and the counts and ids of the problems fixed and broken.

### 3.2 Observe: the model reads its own answers

At the start of each generation $M_{g}$ answers the 500 screen problems once (four samples each). Every editing message carries a summary of this run: accuracy, the distribution of correct samples per problem, the truncation rate, and a few failed problems with statement, gold answer and extracted answer. Two free tools expose the full record: screen\_results filters problems by outcome (all; wrong, unstable or right: 0, 1–3 or 4 of 4 samples correct), and screen\_output pages through any sampled answer including its reasoning. The same answers feed activation statistics: acts(source=’own’) runs the current weights on the problem *plus the model’s own answer* (its first sample), so the editor can contrast how a layer behaves when it reasons correctly and when it fails.

### 3.3 Write: agentic editing sessions

Each candidate is written in one session of the editor $M_{g}$ in thinking mode. The session offers three chat tools: run\_python executes code in a sandboxed Python process that persists across calls (variables, handles and imports survive), read\_record opens the program and feedback of any earlier candidate, and search\_history lists every candidate tried in this and all earlier generations with its modules, rank, tools used and gate outcome. Inside run\_python the editor calls the toolkit in Table 1 through an api object. After at most 30 tool rounds the editor returns a self-contained program main(api) that rebuilds the edit; the program runs in a fresh sandbox and its LoRA is checked against Equation 1. Intermediate edits can be stored with save\_edit and reloaded by the final program.

Table 1: The editor’s toolkit (full signatures in Table 3). $W$: current weight of a module; $(u_{i},\sigma_{i},v_{i})$: its singular triplets. No tool computes a gradient or trains.

| Observe | screen\_results, screen\_output (own answers, reasoning included), train\_example, diagnostics |
| --- | --- |
| Read | svd (top- $k$ triplets of $W$), acts (activation statistics on own answers or prompts), tensors, output\_matrices |
| Construct | rank1 ($s\,uv^{\top}$), from\_direction ($\Delta Wk=\alpha d$), scale\_singular ($\sum_{i}(f_{i}{-}1)\sigma_{i}u_{i}v_{i}^{\top}$), project\_out ($-\alpha\,uu^{\top}W$), direction, unit |
| Compute | tensor\_compute: sandboxed CPU PyTorch on up to four FP32 weight tensors $\to$ statistics, vectors or LoRA factors |
| Operate | scale, interpolate, combine, drop, truncate\_rank, intruder\_scale, orthogonalize, ties, … |
| Check | inspect, train\_loss (forward-only NLL on train problems), compare (fixed / broken problems) |

The toolkit supports edits that are grounded in the model’s own behaviour. A typical construction, suggested in the editor’s prompt, collects activations of one layer on the model’s own correct and incorrect answers, forms the normalised difference $d=(\bar{a}_{\text{wrong}}-\bar{a}_{\text{right}})/\|\bar{a}_{\text{wrong}}-\bar{a}_{\text{right}}\|$, and removes it from the layer’s output matrices with project\_out, which adds the rank-one term $B=-\alpha d$, $A=d^{\top}W$. Other programs rescale a few singular directions of selected modules, add activation directions with from\_direction, or compute exact factors with tensor\_compute; train\_loss provides a cheap forward-only check on train problems before a candidate is graded. Activation statistics and losses are charged to a GPU-time budget, while observation, reading and construction are free. Figure 3 shows a program of this kind.

```
def main(api):
    wrong = [r["id"] for r in api.screen_results(filter="wrong", limit=64)]
    right = [r["id"] for r in api.screen_results(filter="right", limit=64)]
    lora = api.new_lora()["lora"]
    for layer in (44, 48, 52):
        mod = f"layers.{layer}.mlp.down_proj"
        a = api.acts(module=mod, ids=wrong, source="own")
        b = api.acts(module=mod, ids=right, source="own")
        d = api.direction(a=a["handle"] + ".out_mean",
                          b=b["handle"] + ".out_mean")
        for m in api.output_matrices(layer=layer):
            lora = api.project_out(target=lora, module=m["module"],
                                   u=d["vector"], alpha=0.5)["lora"]
    # forward-only sanity check on train problems
    if api.train_loss(lora=lora, n=64)["delta"] > 0:
        lora = api.scale(lora=lora, s=0.5)["lora"]
    return {"lora": lora}
```

### 3.4 Select: hidden gate, merge and succession

Algorithm 1 One generation of SelfWrite.

current model $M_{g}$; gate set $\mathcal{G}$; test set; clean pool $P$; archive and history $\mathcal{A}$

$S_{g}\leftarrow$ 500 problems drawn afresh from $P\setminus(\mathcal{G}\cup\text{test})$; train set $T_{g}\leftarrow P\setminus(\mathcal{G}\cup\text{test}\cup S_{g})$

$M_{g}$ answers $S_{g}$ (4 samples, thinking mode); store answers, reasoning and summary

score $M_{g}$ on $\mathcal{G}$ (4 samples, same decoding and seed)

for $k=1,\dots,8$ do $\triangleright$ independent sessions, run in parallel

  editor $M_{g}$ explores with run\_python, read\_record, search\_history ( $\leq 30$ tool rounds)

  editor returns program $p_{k}$; run $p_{k}$ in a fresh sandbox $\Rightarrow$ LoRA $c_{k}$

  if $c_{k}$ passes the caps (Equation 1) then

   hot-load $c_{k}$ on all replicas; score on $\mathcal{G}$; $\Delta_{k}\leftarrow\Delta_{\mathcal{G}}(c_{k})$ (Equation 3)

   record $\Delta_{k}$, its CI and fixed / broken counts and ids for later generations   

$k^{\star}\leftarrow\arg\max_{k}\Delta_{k}$ over candidates with $\Delta_{k}>0$

if $k^{\star}$ exists then

   $M_{g+1}\leftarrow M_{g}\oplus c_{k^{\star}}$ (Equation 2)

else

   $M_{g+1}\leftarrow M_{g}$

add the generation’s programs and outcomes to $\mathcal{A}$; score $M_{g+1}$ on the test set (logged, never shown to the editor)

A generation runs eight independent sessions in parallel, each producing one candidate. Algorithm 1 summarises one generation. Every candidate is graded once on $\mathcal{G}$ (500 problems, four samples each) and compared with $M_{g}$ by Equation 3; the scores of $M_{g}$ on $\mathcal{G}$ are computed once per generation with the same decoding and seed. The editor never reads a gate problem: sessions of later generations see only each earlier candidate’s accuracy, paired gain, confidence interval and the counts and ids of fixed and broken problems, and no tool accepts a gate id. At the end of the generation, the candidate with the largest strictly positive paired gain is accepted and merged by Equation 2; if none improves, $M_{g}$ is kept. The loop stops after three consecutive generations without an accepted edit. After each generation the current model is also scored on the test split for logging; these scores are never shown to the editor, and we report $M_{0}$ and the final model. Earlier generations’ best programs are shown to the next editor and every attempt stays searchable, so experience accumulates while the editing model itself changes.

#### Safe self-modification.

The loop changes weights only through programs that run in a sandbox without network access, read only train and screen problems, and produce edits that pass the caps in Equation 1. Acceptance is decided by deterministic grading on data the editor cannot read, never by the model’s own judgement, and every accepted edit is a stored program plus a low-rank tensor that a human can audit or revert.

### 3.5 Implementation

The editor writes each LoRA from zero; nothing is trained at any point. Seven data-parallel vLLM \[vllm\] replicas of $M_{g}$ serve the editor, hot-load candidate LoRAs and split the gate problems, and one GPU holds a Transformers copy of $M_{g}$ for SVD, activation statistics, forward losses and merging (Appendix A).

## 4 Experimental Setup

#### Model and data.

We use Qwen3.8-27B \[qwen38\], a dense model with full-attention and Gated DeltaNet layers, as $M_{0}$; the same model is the first editor. All problems come from DAPO-Math-17K \[dapo\] after decontamination against MATH, GSM8K, AIME, AMC and OlympiadBench (exact match after normalisation, or at least half of the 13-grams shared) and removal of internal duplicates, which leaves 14,738 problems. From this pool we fix a gate set of 500 problems and a test set of 500 problems, pairwise disjoint by id and by statement. Each generation draws a fresh screen set of 500 problems from the rest; the remaining 13,238 problems are that generation’s train set.

#### Protocol.

We run five generations of SelfWrite. Each generation has eight independent editing sessions with up to 30 tool rounds each; tool turns and the final turn are capped at 16,384 output tokens, and the editor samples in thinking mode (temperature 0.6, top- $p$ 0.95, top- $k$ 20). Screen, gate and test scoring use the same thinking-mode decoding with four samples per problem (avg@4) and a fixed seed. The candidate with the largest strictly positive paired gain on the gate set is merged. Runs use one node with eight GPUs: seven vLLM \[vllm\] replicas of $M_{g}$ and one tool GPU (Section 3.5); all settings are listed in Table 4.

#### Metrics.

We report the gate accuracy (avg@4) of the current model after every generation, the paired gain $\Delta_{\mathcal{G}}$ of each accepted edit over the model that wrote it (Equation 3), and the test accuracy of $M_{0}$ and of the final model on the 500 test problems, both as avg@4 (mean accuracy over the four samples) and as pass@4 (a problem counts as solved if any of its four samples is correct).

### 5.1 Gains across generations

Table 2 and Figure 4 follow the current model through five generations of SelfWrite. Each generation the edited model writes the next edit, and an edit is merged only when it beats the model that wrote it on the hidden gate, so every accepted step is a paired gain the model produced by editing itself. SelfWrite raises gate accuracy from 73.95% for $M_{0}$ to 76.45% for the final model $M_{5}$, a cumulative gain of 2.50 points. The accepted edits gain +1.20, +0.50, +0.10 and +0.70 points. The first edit brings the largest step, and every later generation, written by a model that has already edited itself, still finds a further improvement; the fourth generation, written by $M_{3}$, brings the second-largest step: the edited model remains an effective editor of its own weights.

### 5.2 Held-out test accuracy

The test split is never screened, gated or shown to the editor, so it measures whether the self-written edits generalise beyond the problems that selected them. On these 500 problems, avg@4 accuracy rises from 76.30% for $M_{0}$ to 77.75% for $M_{5}$ (+1.45 points) and pass@4 from 82.60% to 84.80% (+2.20 points; Table 2) without a single gradient step. The edited model both answers more reliably per sample and solves problems that $M_{0}$ missed in all four samples, so the self-written edits carry over to problems that played no part in selecting them.

## 6 Conclusion

We introduced gradient-free recursive self-editing, in which a language model writes the program that changes its own weights and the edited model writes the next change. SelfWrite grounds each edit in the model’s own reasoning on fresh problems, explores its weights in an agentic session with a white-box toolkit, accepts an edit only on a hidden paired gate, and merges it so the improved model becomes the next editor. On Qwen3.8-27B, five generations raise gate accuracy by 2.50 points (73.95% to 76.45%) and held-out test accuracy by 1.45 points avg@4 (76.30% to 77.75%) and 2.20 points pass@4 (82.60% to 84.80%) without a single gradient step.

#### Discussion.

The loop needs no reward model, no gradient and no human-written edit: the model decides where and how to change its weights from its own answers, and a fixed paired gate decides whether the change is kept. Every gain in Table 2 is therefore a change the model chose for itself, stored as a short program and a low-rank tensor that can be read, rerun or reverted. Because the improved model writes the next edit, the editor improves together with the model it edits. The cost of a generation is dominated by sampling the screen and grading eight candidates, so the loop scales with inference rather than with training.

#### Future work.

Next steps are self-editing across several domains at once, longer horizons with more generations, larger editors, and richer edit spaces beyond low-rank updates, such as edits that change several modules jointly.

### A.2 What the editor sees

The system prompt describes the setting (the editor is the model being edited; edits are merged if they win on the hidden gate), the caps, the toolkit with signatures, the number of tool rounds, and that the session is one of eight independent sessions. Every message carries the summary of the current model’s screen answers, the diagnostics table, the gate outcomes of earlier generations’ candidates (accuracy, paired gain and interval, fixed and broken counts; search\_history and read\_record also list the ids of fixed and broken problems, never their content), and the best programs of earlier generations. Long sessions are compacted: older tool outputs and reasoning are elided once the prompt exceeds 60% of the 131,072-token context.

### A.3 Sandbox and data boundaries

Programs and run\_python code run in a separate process with memory and time limits and no network access; tools are reached only through the api object, and objects are referred to by handles. Activation tools accept only train or screen ids, the statements and answers of gate and test problems are never readable, and the final program must be self-contained: it is re-run from scratch and its output is checked before grading.
